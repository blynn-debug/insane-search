# 스크래핑 차단 진단 지침

> 스크래핑/API 호출이 안 될 때 **"사이트가 API를 막았다/폐지했다"고 성급히 단정하지 말 것.** HTTP 상태코드로 게이트와 폐지를 구분하고, 내 자동화가 원인인지 먼저 의심하라.

## 배경
2026-07 네이버 부동산에서 실제로 이 실수를 했다 — "API 전면 잠김"이라 오진했으나 API는 멀쩡했고, 원인은 자동화 브라우저가 안티봇에 걸린 것뿐이었다. 멀쩡한 파이프라인을 "사망"으로 폐기하고 틀린 정보를 전달할 뻔했다.

## 진단 순서
1. **상태코드로 구분한다.**
   - `404` = 경로 폐지
   - `403` = Referer/권한 게이트
   - `429` = 토큰/쿠키/레이트 게이트
   - SPA가 `/404`로 튕김 = 클라이언트단 봇탐지일 수 있음
   - → **403·429는 "살아있는데 게이트"란 뜻이지 폐지가 아니다.**
2. **내 쪽 원인을 먼저 의심한다.** 헤더(Referer/UA/Accept-Language), 토큰·쿠키 누락, 그리고 특히 **자동화 탐지**(`navigator.webdriver`, HeadlessChrome UA). 사이트를 탓하기 전에 스텔스로 재시도:
   `--disable-blink-features=AutomationControlled` + `navigator.webdriver` 위장 + `window.chrome={runtime:{}}` + 정상 UA + locale.
3. **curl 원샷 실패 하나로 결론내지 않는다.** curl(토큰 없음)과 SPA(봇 튕김)의 서로 다른 실패를 합쳐 "죽었다"고 오판하기 쉽다. 각 경로를 독립적으로 상태코드까지 확인한다.

## 보고 표현
- ❌ "막혔다 / API가 죽었다"
- ✅ "이 상태코드다 → 이 게이트다 → 이걸 시도 중이다"

## 왜 중요한가
성급한 "API 사망" 결론은 (1) 멀쩡히 되는 파이프라인을 폐기시키고, (2) 사용자에게 틀린 정보를 주며, (3) 불필요한 우회 삽질(대체소스 탐색)로 시간을 낭비한다.
